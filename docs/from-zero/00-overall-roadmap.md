## 1. 文档目的

本文描述如何从一个空白 Python 工程开始，逐步建设一个可用、可扩展、可运维的个人 AI Agent 系统。

建设过程的首要目标不是搬运现有 CowAgent 代码，而是完整回答以下问题：

1. 一个最小 AI 助手需要哪些基础组成部分？
2. 普通聊天程序怎样逐步发展为能够自主调用工具的 Agent？
3. 会话、工作空间、技能、记忆和知识库应该在什么阶段加入？
4. 千问、豆包、多模态和多 Agent 如何建立在稳定的核心协议之上？
5. 每增加一种能力，如何通过文档、测试、运行结果和演示证明它已经完成？

当前 CowAgent 是最终能力的重要参考，也是兼容行为、测试场景和成熟实现的来源。但新系统的建设顺序由产品能力和技术依赖决定，不由旧项目的目录结构或历史实现决定。

## 2. 建设目标

最终系统应当具备以下能力：

- 只通过 Web 控制台接收用户消息并呈现运行过程。
- 只接入千问和豆包两类模型服务，并在两者之间提供明确的能力声明和选择策略。
- 以统一的 Agent 循环完成推理、工具选择、工具执行和结果反馈。
- 安全地读写文件、执行命令、访问网络、控制浏览器和调用外部服务。
- 使用工作空间保存角色设定、用户信息、规则、技能、记忆和知识。
- 跨会话保留上下文，并逐步形成长期记忆和结构化知识。
- 支持 Skills、MCP、定时任务、子 Agent 和持续复盘。
- 提供可安装、可升级、可观测、可备份和可恢复的运行方式。
- 保持清晰的模块边界，使千问、豆包、工具、Web 界面和存储可以独立演进。

## 3. 非目标

以下事项不属于 NovaAgent 的建设目标：

- 千问和豆包之外的模型 Provider，包括 OpenAI、Claude、Gemini、DeepSeek、GLM、Kimi、MiniMax 和自定义 Provider。
- Web 控制台之外的用户消息通道，包括终端聊天、飞书、钉钉、Telegram、Discord、Slack、微信、QQ 和桌面客户端。
- 将 CLI 作为聊天入口；CLI 只保留版本、诊断、进程管理和其他开发运维命令。
- 为获得某项视觉、语音、图像或向量能力而引入第三家模型服务；千问和豆包均不支持的能力保持不可用。
- 为了兼容旧实现而保留不必要的全局状态、动态补丁或双重调用链。
- 在核心协议尚未稳定前建设复杂 Web 界面。
- 在基础安全边界尚未建立前开放 Shell、浏览器和任意网络访问。
- 在会话和工作空间尚未清晰分离前建设复杂长期记忆。
- 以测试数量或代码数量代替实际运行和用户可见的阶段成果。

## 4. 建设原则

### 4.1 先形成最小闭环，再扩展能力

每个阶段都必须产生一个可以运行和演示的结果。早期优先完成一条窄而完整的链路，例如“Web 输入 → 千问响应 → Web 输出”，而不是同时铺开多个未连通模块。

### 4.2 先定义协议，再增加实现

消息、模型、工具、会话和事件先形成稳定的核心协议，再接入千问、豆包和 Web 控制台。业务核心不能依赖某个模型 SDK 或 Web 框架的数据结构。

### 4.3 先接入千问，再补充豆包

先使用千问、Web 控制台、一个会话存储和一组基础工具形成闭环。千问经过实际验证后，再接入豆包并抽象两者确实需要的扩展点；Provider 范围固定为这两家，不继续扩展。

### 4.4 功能设计优先于旧代码复用

每个阶段先描述用户价值、功能边界和新系统设计，最后才分析现有项目的参考价值。允许复用成熟算法和安全处理，但不能为了直接复制代码而破坏新架构。

### 4.5 默认安全，显式授权

文件、命令、网络、浏览器、凭据和外部消息发送均属于有副作用能力。工具必须有明确的工作目录、输入校验、权限范围、超时、取消、输出限制和审计事件。

### 4.6 状态归属必须明确

进程配置、Agent 工作空间、用户会话、项目目录和临时执行状态必须分开。任何持久化数据都要能回答“属于哪个 Agent、哪个用户、哪个会话，以及由谁负责清理”。

### 4.7 文档和代码同步演进

设计文档不是开发后的说明书，而是进入编码前必须完成的设计输入。实现过程中如果改变了边界、接口或验收方式，必须先更新设计，再完成代码。

### 4.8 兼容通过边界处理

旧配置、旧工作空间和旧数据的兼容由转换器、适配器或导入工具负责，不把历史格式扩散到核心领域模型中。

## 5. 新代码总体架构

新系统采用模块化单体作为起点。所有功能在一个代码仓库和一个主要进程内协作，但内部拥有明确的层次和依赖方向。只有当实际部署需求证明有必要时，才拆分独立服务。

### 5.1 逻辑分层

```text
┌─────────────────────────────────────────────────────────────┐
│ Interfaces                                                  │
│ Web Console · Web API                                       │
└──────────────────────────────┬──────────────────────────────┘
                               │ commands / queries
┌──────────────────────────────▼──────────────────────────────┐
│ Application                                                 │
│ Chat · Agent Run · Sessions · Workspace · Tasks             │
└──────────────────────────────┬──────────────────────────────┘
                               │ domain contracts
┌──────────────────────────────▼──────────────────────────────┐
│ Domain                                                      │
│ Message · Content · Agent Event · Tool Call · Session       │
│ Model / Tool / Store ports · policies                       │
└──────────────────────────────▲──────────────────────────────┘
                               │ implementations
┌──────────────────────────────┴──────────────────────────────┐
│ Infrastructure                                              │
│ Qwen · Doubao · SQLite · Filesystem · MCP · Browser         │
│ Scheduler · Search                                          │
└─────────────────────────────────────────────────────────────┘

Bootstrap 负责配置加载、依赖装配、生命周期和进程启动。
Observability 与 Security 作为横切能力覆盖所有层。
```

### 5.2 各层职责

#### Domain：核心协议与规则

Domain 只表达系统中稳定且与具体技术无关的概念：

- `Message`：一条带角色、内容块和元数据的消息。
- `ContentBlock`：文本、图片、音频、文件、工具调用和工具结果。
- `ModelRequest` / `ModelResponse`：模型输入和输出。
- `AgentEvent`：推理、文本增量、工具开始、工具结束、错误和完成事件。
- `ToolDefinition` / `ToolCall` / `ToolResult`：工具协议。
- `Session`：会话标识、消息历史和生命周期。
- `AgentProfile`：Agent 身份及其工作空间归属。
- 各类 Port：模型、工具、存储和事件输出所需的抽象接口。
- 策略：最大步骤数、上下文预算、超时、权限和重试规则。

Domain 不导入千问或豆包 SDK、Web 框架或数据库驱动。

#### Application：用例与编排

Application 负责把核心协议组织成可执行用例：

- 单轮和多轮聊天。
- 会话创建、恢复、压缩和清理。
- Agent 的模型调用与工具调用循环。
- 工作空间加载和提示词组装。
- Skill 发现和选择。
- 记忆提取、检索和写入。
- 定时任务和子 Agent 编排。
- 将执行过程转换为统一事件流。

Application 可以依赖 Domain，但不能直接依赖某个具体供应商 SDK。

#### Infrastructure：技术实现

Infrastructure 实现 Domain 定义的 Port：

- 千问和豆包模型适配器。
- SQLite 会话、记忆和任务存储。
- 文件系统工作空间和原子写入。
- 本地工具、网络工具、浏览器和 MCP 客户端。
- 向量嵌入和检索后端。
- 日志、指标和追踪输出。

#### Interfaces：用户与外部入口

Interfaces 将 Web 输入转换为应用用例，并将 `AgentEvent` 转换为 Web 输出：

- Web 控制台及其 HTTP API、SSE 或 WebSocket 协议。
- 版本、诊断和进程管理等非聊天 CLI。

Interfaces 不实现终端聊天、第三方即时通信渠道或桌面客户端。

Interfaces 不实现 Agent 决策逻辑，也不直接读写长期记忆。

#### Bootstrap：装配与生命周期

Bootstrap 负责：

- 加载和校验配置。
- 创建模型、工具、存储和应用服务实例。
- 管理启动、停止、信号和后台任务。
- 暴露健康检查和诊断信息。
- 启动唯一的用户入口 Web 控制台，并按需提供非聊天管理命令。

### 5.3 依赖规则

必须遵守以下规则：

1. Domain 不依赖其他业务层。
2. Application 只依赖 Domain 和抽象 Port。
3. Infrastructure 依赖 Domain，并实现 Port。
4. Interfaces 依赖 Application 和 Domain，不绕过 Application 操作存储。
5. Bootstrap 可以引用所有层，但只负责装配，不承载业务规则。
6. 模型、工具和 Web 接口之间不能互相直接调用。
7. 持久化对象不能直接泄漏数据库行或第三方 SDK 对象。
8. 旧系统兼容代码只能存在于明确的适配或导入边界。

## 6. 核心执行流程

### 6.1 普通聊天流程

```text
Web 控制台输入
  → 接口层转换为统一 Message
  → Chat Application Service 加载会话
  → Prompt / Context 组装
  → Model Port
  → Provider Adapter 调用模型
  → 统一 AgentEvent 流
  → 接口层渲染并返回用户
  → Session Store 持久化最终消息
```

### 6.2 Agent 工具调用流程

```text
用户输入
  → 加载会话、工作空间和可用工具
  → 调用模型
  → 模型返回文本或 ToolCall
      ├── 文本：输出并结束
      └── ToolCall：
          → 权限与参数校验
          → 执行工具并产生事件
          → ToolResult 加入上下文
          → 再次调用模型
          → 达到完成条件或安全上限后结束
```

### 6.3 状态边界

```text
进程级：应用配置、Provider 注册表、全局健康状态
Agent 级：身份、工作空间、规则、技能、长期记忆
会话级：消息历史、上下文摘要、取消状态、项目目录
执行级：当前步骤、工具调用、流式事件、临时产物
```

任何新增功能必须明确它属于哪一级状态，并设计相应的创建、访问、并发和清理规则。

## 8. 各阶段建设内容

### 阶段 01：产品边界与工程地基

#### 要解决的问题

空白项目首先需要稳定、可重复的开发环境。如果安装、测试、启动和配置方式不统一，后续每种能力都会建立在不可靠的基础上。

#### 本阶段工作

- 明确产品第一版用户、使用场景、最小范围和非目标。
- 确定 Python 版本、包管理方式、`src/` 布局和模块命名。
- 建立统一 `pyproject.toml`、开发依赖和锁定策略。
- 建立配置模型、环境变量规则、密钥边界和默认目录。
- 建立结构化日志、统一异常和退出码。
- 建立单元测试、集成测试、格式检查和静态检查入口。
- 实现最小管理 CLI，包括版本、帮助、`doctor` 和 Web 服务启动命令；不提供终端聊天。
- 建立 CI 和本地一键验证命令。

#### 最小演示

在一个干净环境中完成安装，运行 `doctor` 检查环境，启动程序后得到明确健康状态，并执行第一条自动测试。

#### 核心验收方向

- 新开发者仅依据 README 即可完成安装和验证。
- 配置错误在启动前给出可理解的提示。
- 运行测试不依赖真实模型密钥。
- 源码包、测试和文档边界清晰。

#### 现有项目参考与复用

参考当前 CLI、启动脚本、Docker 和配置项覆盖的实际部署场景；重新设计工程元数据和配置入口，不直接复制历史启动编排。

### 阶段 02：核心消息与事件协议

#### 要解决的问题

Web、模型和工具必须使用同一种内部语言，避免前端协议、模型响应和工具事件形成彼此割裂的调用链。

#### 本阶段工作

- 定义角色、消息、内容块和消息元数据。
- 定义文本、图片、音频、文件、工具调用和工具结果的表达方式。
- 定义流式 `AgentEvent` 类型及顺序约束。
- 定义模型、事件接收器和会话存储的最小 Port。
- 定义序列化格式、版本字段和未知字段处理规则。
- 建立假模型和内存事件接收器，用于确定性测试。
- 建立协议契约测试和事件快照测试。

#### 最小演示

测试驱动程序将一条输入转换为统一消息，假模型产生多个文本事件，内存事件接收器按顺序得到完整回复；它只用于协议验证，不作为用户聊天入口。

#### 核心验收方向

- Domain 不导入任何模型或 Web SDK。
- 同一事件流可以被 Web 接口和测试接收器消费。
- 非法事件序列和不支持的内容类型有明确错误。
- 协议可以向后兼容地增加字段。

#### 现有项目参考与复用

参考当前 `bridge/context.py`、`bridge/reply.py`、`agent/protocol/` 和 Web 流式事件的实际消息种类；重新统一命名和边界，避免同时维护普通聊天与 Agent 两套协议。

### 阶段 03：千问接入与 Web 单轮聊天

#### 要解决的问题

核心协议需要连接一个真实大模型，形成系统的第一条外部能力闭环。

#### 本阶段工作

- 定义模型能力、请求选项、使用量和标准错误。
- 实现千问 / DashScope Provider Adapter。
- 实现模型配置、密钥读取、超时、重试和速率限制基础规则。
- 实现非流式单轮聊天应用服务。
- 实现只支持单轮聊天的最小 Web 页面和 API，作为唯一用户入口的第一版。
- 区分鉴权错误、限流、超时、输入错误和供应商服务错误。
- 使用假 HTTP 服务完成集成测试，真实 API 仅用于人工验收。

#### 最小演示

用户在浏览器输入一个问题，系统通过千问返回完整文本答案，并在页面显示模型名称、耗时和使用量摘要。

#### 核心验收方向

- 核心聊天用例不感知 DashScope SDK 或 HTTP 响应对象。
- 没有密钥时能启动诊断，但不能误发请求。
- 网络错误不会泄露密钥或完整敏感请求。
- Provider 可被假实现替换并稳定测试。

#### 现有项目参考与复用

参考当前 DashScope 与 OpenAI-compatible HTTP 处理、供应商错误兼容和模型配置经验；只提取千问需要的响应解析与错误分类，不保留通用自定义 Provider 入口，也不延续运行时动态修改 Bot 类的方式。

### 阶段 04：Web 流式输出与多轮会话

#### 要解决的问题

单轮完整回复无法提供良好的交互体验，也无法让模型理解连续对话。系统需要统一的流式输出和会话生命周期。

#### 本阶段工作

- 实现模型流式响应到 `AgentEvent` 的转换。
- 实现会话创建、选择、消息追加、清空和关闭。
- 扩展阶段 03 的最小 Web 页面和 API，支持流式输出、多轮会话与取消操作。
- 实现内存会话存储和并发访问规则。
- 组装系统消息、历史消息和当前用户消息。
- 建立上下文轮次限制和初步 token 预算接口。
- 实现取消当前生成和客户端断开处理。
- 测试流式分片、半途失败、取消和多会话隔离。

#### 最小演示

在两个浏览器会话中分别连续对话；千问回复实时显示，取消一个会话不会影响另一个会话。

#### 核心验收方向

- 流式与非流式输出得到一致的最终文本。
- 同一会话内消息顺序确定，不同会话互不污染。
- 取消后停止继续输出并释放执行资源。
- 上下文超限前有可观测且可测试的处理。

#### 现有项目参考与复用

参考当前流式事件、会话恢复、取消和并行 session 的测试场景；新系统先实现清晰的会话状态机，再考虑旧会话数据导入。

### 阶段 05：Agent 决策循环

#### 要解决的问题

聊天模型只能生成内容，Agent 还需要识别工具请求、执行工具、反馈结果并继续决策，直到任务结束或达到安全上限。

#### 本阶段工作

- 定义工具 Schema、工具调用和工具结果协议。
- 实现工具注册表和一个无副作用示例工具。
- 实现 Agent 步骤循环、完成条件和最大步骤数。
- 将工具开始、进度、结果和错误转换为统一事件。
- 实现工具结果回填模型上下文。
- 实现未知工具、错误参数、工具失败和模型空响应处理。
- 支持取消、总超时和步骤级超时。
- 使用脚本化假模型覆盖所有决策分支。

#### 最小演示

用户询问一个必须借助示例工具才能回答的问题，模型请求工具，系统执行并回填结果，模型生成最终答案。

#### 核心验收方向

- 一次 Agent Run 的状态变化可完整追踪。
- 无限工具循环会被步骤或时间上限终止。
- 工具错误不会破坏会话历史。
- 不依赖真实模型即可确定性复现多步骤任务。

#### 现有项目参考与复用

参考当前 `Agent`、流式执行器、工具事件和并行工具调用测试；重新实现精简状态机，避免让 Agent 实例同时承担提示词、工作目录、技能、记忆和持久化的全部职责。

### 阶段 06：安全的本地工具

#### 要解决的问题

真实 Agent 必须操作文件和命令，但这些能力直接影响用户数据和系统安全，需要先建立统一工具运行时，再扩展工具数量。

#### 本阶段工作

- 实现 `ls`、`read`、`search_files`、`write` 和 `edit`。
- 在文件修改稳定后实现受控 `bash`。
- 建立工作目录、路径归一化、符号链接和路径穿越防护。
- 建立写入前状态检查、原子写入和差异输出。
- 建立命令超时、后台任务、输出截断和编码处理。
- 建立工具可用性、危险操作和确认策略接口。
- 建立敏感文件、环境变量和凭据保护规则。
- 添加安全回归、并发修改和跨平台测试。

#### 最小演示

Agent 在指定沙箱目录内读取一个文件、生成修改、展示差异并运行一条验证命令；越界路径和超时命令被拒绝。

#### 核心验收方向

- 工具不能越过配置的工作目录访问文件。
- 文件写入失败不留下半写状态。
- Shell 命令可取消、可超时、可限制输出。
- 每次有副作用的执行都有可审计事件。

#### 现有项目参考与复用

优先参考现有文件工具、Shell 后台执行、输出编码、语法检查、SSRF 和路径安全测试。安全算法可以提取复用，但工具生命周期和配置方式按新运行时重新组织。

### 阶段 07：Web 控制台完善

#### 要解决的问题

阶段 03 和阶段 04 已形成最小 Web 聊天入口，但仍需要完整呈现工具过程、文件、错误、配置状态和会话管理。

#### 本阶段工作

- 完善阶段 03、04 已建立的 Web API 框架和前端工程。
- 实现健康检查、配置状态和聊天 API。
- 使用 SSE 或 WebSocket 转发统一事件流。
- 实现会话列表、创建、选择、清空和删除。
- 实现聊天界面的 Markdown、代码块、工具卡片和错误状态。
- 建立认证、跨域、请求大小和上传边界。
- 建立 API 契约测试、前端测试和浏览器端到端测试。

#### 最小演示

浏览器中创建两个会话，观察流式文本与工具卡片，刷新页面后仍能正确识别当前会话状态。

#### 核心验收方向

- Web 只消费统一事件，不包含模型供应商特例。
- 断线、重连和取消行为明确。
- 未认证用户不能访问受保护配置和数据。
- Web API 与控制台对同一 Agent Run 呈现一致最终结果。

#### 现有项目参考与复用

参考当前 Web 控制台已验证的交互需求、静态资源离线策略和流式工具卡片行为；协议和后端服务重新建立，UI 组件按可复用价值逐项评估。

### 阶段 08：工作空间与提示词

#### 要解决的问题

一个个人 Agent 不应把身份、用户偏好和行为规则硬编码在程序中，需要可读、可编辑、可版本管理的工作空间。

#### 本阶段工作

- 定义 Agent 工作空间和项目工作目录的区别。
- 设计 `AGENT.md`、`USER.md`、`RULE.md` 等核心上下文文件。
- 实现工作空间创建、校验和安全路径解析。
- 实现 Prompt Assembly Pipeline 和各区块优先级。
- 实现 token 预算、内容截断和运行时信息注入。
- 支持核心文件热更新和会话提示词刷新。
- 建立提示词快照、优先级和异常文件测试。

#### 最小演示

用户修改角色或规则文件，无需重启即可在下一轮对话观察行为变化；切换项目目录只改变工具工作目录，不改变 Agent 身份。

#### 核心验收方向

- 工作空间数据和项目文件不会混淆。
- Prompt 每一部分都有来源和预算。
- 文件缺失、格式错误和内容过大均可安全处理。
- 核心文件修改不会影响其他 Agent 工作空间。

#### 现有项目参考与复用

参考当前工作空间文件、动态 Prompt 重建和项目目录切换行为；保留用户可读的 Markdown 资产形式，重新设计 Prompt 组装职责和缓存边界。

### 阶段 09：Skills 扩展系统

#### 要解决的问题

工具表达原子能力，但复杂任务还需要可阅读、可安装和可复用的工作流说明。Skills 应建立在稳定的工具和工作空间之上。

#### 本阶段工作

- 定义 Skill 目录、元数据、正文和版本格式。
- 实现发现、解析、校验、启用和禁用。
- 实现平台、二进制、环境变量和配置依赖检查。
- 实现按需加载和提示词预算控制。
- 实现本地安装、卸载和更新的事务边界。
- 规定 Skill 与工具、凭据和工作空间的权限关系。
- 建立恶意路径、重复名称、无效元数据和缺失依赖测试。

#### 最小演示

安装一个本地 Skill，Agent 识别其适用场景，读取说明并组合已有工具完成一项多步骤任务。

#### 核心验收方向

- Skill 不能绕过工具运行时的安全限制。
- 无法满足依赖的 Skill 会解释原因而不是静默失效。
- 大量 Skill 不会无条件占满模型上下文。
- 安装失败不会留下部分文件或损坏既有 Skill。

#### 现有项目参考与复用

参考当前 Skill frontmatter、依赖检测、Skill Hub 安装和 `skill-creator` 工作流；优先兼容通用 Skill 内容格式，安装和加载服务按新边界实现。

### 阶段 10：持久化与长期记忆

#### 要解决的问题

内存会话在进程重启后会丢失，也无法让 Agent 跨会话保留有价值的信息。持久化、上下文管理和长期记忆需要分层建设。

#### 本阶段工作

- 实现 SQLite 会话和消息存储。
- 定义事务、并发、恢复、清理和 Schema 版本策略。
- 实现会话历史恢复和上下文窗口选择。
- 实现上下文摘要和压缩。
- 定义日级记忆与核心记忆的职责。
- 实现记忆提取、人工确认策略、写入和检索。
- 建立关键词检索，再按需要增加向量检索 Port。
- 实现备份、重建索引和损坏恢复基础能力。

#### 最小演示

用户告诉 Agent 一项偏好，关闭并重启程序，在新会话中通过记忆检索正确使用该偏好，同时可以查看其来源。

#### 核心验收方向

- 会话历史、长期记忆和知识库使用不同的数据语义。
- 记忆写入有来源、时间和可撤销能力。
- 数据库损坏或索引失效时有可理解的恢复路径。
- 不同 Agent 和会话之间不存在数据串用。

#### 现有项目参考与复用

参考当前 SQLite 会话、日级/核心记忆、混合检索、向量后端和 Deep Dream 经验；数据格式兼容放在导入器中，新领域模型不直接继承历史表结构。

### 阶段 11：个人知识库

#### 要解决的问题

记忆按时间和个人经历组织，无法替代按主题维护的结构化资料。知识库需要独立的内容模型、索引和引用关系。

#### 本阶段工作

- 定义知识页面、分类、标签、来源和链接。
- 采用 Markdown 作为可读的主要内容格式。
- 实现页面创建、更新、移动、删除和索引维护。
- 实现全文搜索和引用关系提取。
- 设计从对话候选信息到知识页面的整理流程。
- 实现冲突检测、重复内容和安全文件名处理。
- 在 Web 控制台提供列表、预览、搜索和关系浏览。

#### 最小演示

Agent 将一段对话整理成主题页面，更新知识索引；用户随后通过搜索找到页面并追溯到来源。

#### 核心验收方向

- 记忆不会被误当作知识页面直接写入。
- 页面和索引更新保持一致性。
- 所有自动整理结果可查看、修改和撤销。
- 页面链接不能越过知识库目录。

#### 现有项目参考与复用

参考当前 Markdown Wiki、分类、索引和知识图谱展示；保留人类可读资产，重新定义应用服务和原子更新策略。

### 阶段 12：外部能力与自动任务

#### 要解决的问题

成熟 Agent 需要访问网页、浏览器和外部工具生态，也需要在没有即时用户输入时执行计划任务。这些能力具有更复杂的网络和生命周期风险。

#### 本阶段工作

- 实现 `web_fetch`、搜索和视觉工具。
- 实现浏览器服务、浏览器工具和进程生命周期。
- 实现 MCP stdio 与 HTTP 连接、工具发现和热更新。
- 实现定时任务模型、持久化、运行历史和手动触发。
- 设计后台任务与普通会话的隔离。
- 建立 URL 安全、SSRF、防重入、超时和资源限额。
- 实现外部工具按需发现，控制模型上下文规模。

#### 最小演示

Agent 安全抓取指定网页，通过一个 MCP 工具处理信息，并创建一个可手动立即执行的定时任务；所有过程在 Web 中可见。

#### 核心验收方向

- 内网、元数据地址和危险重定向被阻止。
- MCP Server 故障不会拖垮主进程。
- 定时任务重复触发、重启恢复和取消行为确定。
- 后台任务不能把结果写入错误的 Web 用户或会话。

#### 现有项目参考与复用

参考当前 URL 安全、MCP 多传输协议、工具检索、浏览器单例和 Scheduler 测试；成熟的安全校验可以迁移，服务生命周期按新 Bootstrap 统一管理。

### 阶段 13：多 Agent 与持续复盘

#### 要解决的问题

单个 Agent 工作空间无法覆盖多角色隔离、并行任务和专门代理。自动复盘又需要在不干扰主对话的前提下安全修改工作空间。

#### 本阶段工作

- 定义 Agent Profile、工作空间所有权和路由规则。
- 将运行时键明确为 Agent 与 Session 的组合。
- 实现多工作空间存储、工具、技能、记忆和任务隔离。
- 实现受控子 Agent 和 Agent 间委派。
- 建立深度、循环、并发、超时、取消和结果大小限制。
- 实现对话空闲后的复盘触发和隔离执行。
- 实现修改前备份、写入白名单、变更记录和回滚。

#### 最小演示

两个拥有独立工作空间的 Agent 同时运行；主 Agent 将一个受限任务交给子 Agent，并显示其过程和来源；复盘产生的修改可以查看和撤销。

#### 核心验收方向

- 相同 Session ID 不会导致不同 Agent 共享状态。
- 委派无法无限递归或绕过禁用目标。
- 子 Agent 不能访问未授权工具和工作空间。
- 自动复盘不能修改受保护文件或静默覆盖用户内容。

#### 现有项目参考与复用

参考当前多 Agent Registry、Routing、Subagent Runner 和 Evolution 安全事务；以现有多 Agent 设计中的隔离约束作为兼容基线，但在新核心协议上重新实现。

### 阶段 14：豆包接入与多模态

#### 要解决的问题

核心能力稳定后，系统需要在千问之外接入豆包，并在唯一的 Web 控制台中处理两家服务实际支持的图片、语音、文件等内容，同时避免供应商特例污染核心。

#### 本阶段工作

- 接入豆包 Provider，与阶段 03 的千问 Provider 共同组成固定白名单。
- 建立千问和豆包的能力声明、模型选择与显式降级策略。
- 建立两家 Provider 的契约测试，验证文本、流式、工具调用和推理事件。
- 在 Web 控制台中实现图片、文件及两家 Provider 实际支持的多模态内容流。
- 对千问和豆包均不支持的 ASR、TTS、图像生成或向量能力返回明确的不可用状态，不接入第三家服务补齐。
- 完善模型配置校验，拒绝其他 Provider、自定义模型端点和其他聊天通道配置。

#### 最小演示

同一 Agent 会话核心可以选择千问或豆包运行，并只从 Web 控制台接收文本、图片或文件；两家模型产生的最终事件语义保持一致。

#### 核心验收方向

- 千问和豆包之间切换不修改 Agent 循环。
- Web 控制台不包含千问或豆包的专用业务分支。
- 不支持的能力在调用前被识别，而不是运行时随机失败。
- Web 用户、会话和附件归属可追踪且互不串用。
- 任何非白名单 Provider 或非 Web 聊天通道配置都会在启动校验时被拒绝。

#### 现有项目参考与复用

只评估 CowAgent 中与千问、豆包和 Web 控制台直接相关的实现。其他模型、终端聊天、即时通信渠道和桌面端仅作为明确排除项记录，不迁移其 SDK、签名校验或消息适配代码。

### 阶段 15：运维与正式交付

#### 要解决的问题

功能可用不等于产品可交付。用户还需要可靠安装、升级、诊断、备份、恢复和 Web 服务运行能力。

#### 本阶段工作

- 完成 CLI 进程管理、日志查看和诊断。
- 完成本地、Docker 和服务器部署方式。
- 建立配置和数据 Schema 升级机制。
- 建立备份清单、恢复事务和回滚策略。
- 增加健康检查、结构化日志、指标和问题报告包。
- 完善 Web 服务的进程管理、认证、反向代理和安全部署说明。
- 完成安全审查、性能基线和故障演练。
- 编写用户文档、管理员文档和开发者文档。
- 制定旧系统停用和回退窗口。

#### 最小演示

在干净机器上安装并启动应用，导入已有工作空间，完成聊天和工具调用，备份数据，升级应用，再恢复备份并验证关键数据。

#### 核心验收方向

- 安装、升级和恢复均有可重复验证流程。
- 失败升级不会破坏用户工作空间。
- 密钥不进入备份、日志或诊断包。
- Docker 和源码运行共享同一 Web 控制台行为。

#### 现有项目参考与复用

参考当前 CLI、Docker、启动脚本和备份能力。外围脚本只有在适配 Web 唯一入口和新目录后复用；桌面端打包不迁移，旧配置与数据通过显式兼容工具处理。

## 9. 每个阶段的强制交付方式

每个阶段都必须形成完整闭环。以下八项是不可跳过的阶段门禁，不是建议顺序。

### 9.1 先写本阶段设计文档

在修改本阶段业务代码前创建并完成 `design.md`。设计文档必须从完善系统功能的角度说明用户价值、问题、目标、非目标、架构、接口、状态、安全边界、测试和演示方式。

旧项目参考只能出现在主体设计之后，不能成为功能目标或架构选择的唯一理由。

### 9.2 列出验收标准

验收标准必须在编码前确定，并且满足：

- 可观察，而不是“结构合理”一类主观描述。
- 可执行，能够通过测试、命令或演示验证。
- 同时覆盖正常路径、失败路径和关键安全边界。
- 明确本阶段结束时用户能够完成什么。

### 9.3 实现最小代码

只实现达到本阶段验收标准所需的最小完整代码：

- 不预先实现后续阶段的复杂扩展。
- 不留下只能依靠未来代码才能运行的半成品。
- 需要扩展点时先用最小接口表达，不建立未经验证的框架。

### 9.4 添加测试

根据阶段风险选择测试层次：

- Domain 规则使用单元测试。
- Port 实现使用契约测试。
- 数据库、文件系统和 HTTP 边界使用集成测试。
- 用户关键流程使用端到端测试。
- 安全问题必须有对应回归测试。

不得把真实付费模型作为自动化测试的必要条件。

### 9.5 实际运行验证

测试通过后必须按照设计文档中的运行步骤实际启动系统，走通最小演示。运行记录至少包含：

- 环境与配置前提。
- 执行命令。
- 关键输出。
- 发现的问题及处理结果。

实际运行不能被“代码可导入”或“单元测试通过”替代。

### 9.6 记录与现有 CowAgent 的差异

在阶段完成报告中记录：

- 新系统已经覆盖的行为。
- 有意改变的行为及原因。
- 尚未覆盖的能力。
- 复用、重写、适配或废弃的旧实现。
- 配置、数据和用户操作上的兼容影响。

差异记录用于理解设计演进，不以代码行数相同或完全复刻为目标。

### 9.7 更新进度表

更新本文的阶段状态，并更新 `legacy-reference-progress.md` 中相关能力的设计、实现、测试、验收和兼容状态。没有证据的状态不得标记为完成。

### 9.8 完成可演示成果后进入下一阶段

本阶段必须形成一个他人可以按照文档复现的演示。完成报告要给出演示步骤、预期结果和已知限制。

只有以下材料全部存在并一致时，阶段才算完成：

- 已确认的设计文档。
- 明确的验收标准。
- 达标的最小实现。
- 通过的自动化测试。
- 成功的实际运行记录。
- 完整的差异记录。
- 已更新的进度表。
- 可复现的阶段演示。

任何一项缺失，下一阶段保持“未开始”。

阶段 01 的验收采用一次性组合证据决策：GitHub Actions 提供干净安装和质量检查证据，此前真实 Web 进程运行记录提供启动、端点访问和停止证据。项目负责人确认该组合满足阶段 01 演示门禁；这项决策已记录在阶段 01 完成报告中，不自动豁免后续阶段的演示要求。

## 10. 阶段设计文档模板

每个阶段创建独立目录，至少包含 `design.md`。阶段完成时增加 `completion-report.md`。

### 10.1 `design.md` 必备结构

```text
# 阶段 NN：名称

## 1. 背景与用户价值
## 2. 当前能力与本阶段问题
## 3. 本阶段目标
## 4. 非目标
## 5. 使用场景
## 6. 功能设计
## 7. 架构与模块设计
## 8. 核心接口和数据结构
## 9. 数据流与执行流程
## 10. 配置和运行方式
## 11. 异常、安全与边界情况
## 12. 测试方案
## 13. 验收标准
## 14. 最小演示方案
## 15. 实施任务清单
## 16. 现有 CowAgent 参考与复用策略
## 17. 预期差异
## 18. 设计决策记录
```

设计决策记录用于保存本阶段的重要取舍。若某项决定影响多个阶段，应同时创建独立 ADR 并在此引用。

### 10.2 `completion-report.md` 必备结构

```text
# 阶段 NN 完成报告

## 1. 完成范围
## 2. 实际实现
## 3. 验收结果
## 4. 自动化测试记录
## 5. 实际运行记录
## 6. 演示步骤与结果
## 7. 与设计的偏差
## 8. 与现有 CowAgent 的差异
## 9. 旧实现处理记录
## 10. 已知限制和遗留事项
## 11. 文档与进度表更新
## 12. 阶段结论
```

阶段结论只能是：

- `通过`：八项门禁全部完成，可以进入下一阶段。
- `未通过`：仍有门禁未完成，不得进入下一阶段。

## 13. 现有 CowAgent 的使用方式

现有 CowAgent 在建设过程中承担四种角色：

1. **产品参考**：确认最终系统已经被用户使用的能力和交互细节。
2. **行为基线**：通过现有测试、配置和运行结果理解边界条件。
3. **实现素材**：复用成熟的协议解析、安全校验、平台 SDK 交互或算法。
4. **数据来源**：验证旧工作空间、配置和数据库的兼容或导入流程。

现有 CowAgent 不承担以下角色：

- 不决定新系统模块边界。
- 不决定功能建设顺序。
- 不要求保留全部历史内部 API。
- 不要求逐文件或逐目录迁移。
- 不以新旧代码结构相似作为完成标准。

具体能力的参考和处理状态统一记录在 `legacy-reference-progress.md`，避免迁移信息占据阶段功能设计主体。

## 14. 总体验收原则

整个从零建设过程完成时，不仅要得到一个功能完整的新系统，还要留下可以复盘的工程轨迹：

- 每项能力为什么在对应阶段加入。
- 加入之前系统存在哪个真实问题。
- 采用了什么协议和模块边界。
- 哪些失败路径和安全风险被考虑。
- 自动化测试和实际运行如何证明能力成立。
- 与成熟 CowAgent 相比有哪些一致、改进和暂未覆盖之处。
- 如何从早期最小产品逐步演进到完整系统，而不推翻已经稳定的核心。

最终交付物是“可运行系统 + 全阶段设计记录 + 全阶段完成报告 + 可复现演示 + 现有能力参考进度”，而不只是最终源码。
